Cordis

The plugin kernel under DeepSeek Harness, and under everything in ACRYL.

A kernel that grew up in chatbots

  • Koishi: a cross-platform chatbot framework (Discord, Telegram, Matrix and more) with 4,000+ community plugins
  • Cordis (2022): its plugin kernel, extracted as a meta-framework. It knows nothing about LLMs, agents or tools
  • DeepSeek Harness forked it (@deepseek-ai/cordis) and built the agent on top: model adapters, tools, sessions, sandboxes, the UI, all plugins
  • Backed by a paper: A Programming Paradigm for Spatiotemporal Composability, Peking University and DeepSeek-AI

The session lives longer than its parts

A group chat or a coding session runs for days. Its capabilities arrive, leave and get replaced while it runs. Cordis guarantees two things so that never breaks it:

Temporal composability

When a component leaves, everything it did to the shared environment is reverted: routes, tools, timers, subscriptions. No residue, and unrelated work survives.

Spatial composability

Components declare what they need. A consumer activates only when its requirements exist, and stops cleanly before its provider is withdrawn.

component = requirements + provisions + effects with undo

One plugin, mounted: a Fiber with its own Context

Context: the world a plugin may see and change

  • Find capabilities by name: ctx.llm, ctx.tools
  • Own what it creates: ctx.effect, ctx.plugin, ctx.on
  • Talk through typed events: ctx.emit, ctx.waterfall
  • Scope the world below it: extend for metadata, isolate for a separate service, intercept for scoped config

Isolation changes which provider a name resolves to. It is not a security sandbox.

Fiber: the lifecycle of one mounted plugin

PENDING is not an error: the plugin is mounted and waiting for its environment. Losing a dependency sends it back to PENDING, not to DISPOSED.

A plugin waits for what it needs, and leaves no trace

      Every registration is an effect with an inverse. Unloading runs the inverses in reverse order. States: PENDING, LOADING, ACTIVE, FAILED, UNLOADING, DISPOSED.

      Services and inject: depend on a name, not on a provider

      Events: five ways to dispatch

      Use a service call when you need one answer from a known capability; use an event when the producer should not know who listens.

      Waterfall: middleware around a default

      Each listener receives the input and next. Call next() to continue to the inner layer; return without it to answer or veto.

      An observer that logs, measures or annotates must call next(). Event listeners are effects too: they disappear when their plugin unloads.

      Effects: everything comes with its undo

      Every resource a plugin acquires lives inside an owned effect with a disposer. Unloading runs the disposers newest first, once.

      That is why a plugin can be removed, replaced or hot-reloaded while the session keeps running.

      Loader: rows of YAML become the live plugin tree

      All of it in one small plugin

      • Context: the scoped environment a plugin receives; services, events and effects live on it
      • Service: a named capability, ctx.tools, ctx.llm; replaceable by another provider
      • inject: a live dependency contract, not a load order
      • Effects: everything a plugin acquires is owned and released with it
      • Loader: rows in cordis.patch.yml become the live plugin tree; change a row, the tree updates
      // a Cordis plugin, simplified: needs the tools service, adds one tool
export const name = 'word-count'
export const inject = ['tools']

export function apply(ctx) {
  ctx.tools.register(defineTool({
    name: 'word_count',
    description: 'Count words in a text',
    parameters: { text: { type: 'string' } },
    async execute({ text }) {
      return text.split(/\s+/).filter(Boolean).length
    },
  }))
  // unloading the plugin unregisters the tool: no cleanup code
}

      It composes a running process. It does not describe, version or share an app.

      No app definition

      A profile is a local list of bundles on one machine. There is no file that says "this is my app" and travels.

      No reproducibility

      No lock of exact versions and checksums; two machines drift apart.

      No sharing

      No registry of whole apps, no verified pull, no way to start from someone else's setup and keep their updates.

      That gap is why the DeepSeek Harness community already has thousands of plugins that solve the same problems again and again.

      ACRYL Blends

      A protocol for composable software that people can share and reuse.

      Cordis composes; Blends describes, locks, shares and grows

      An app in one file

      • kind: a Blueprint to start from, or a Blend grown from one
      • extends: inherit another app's rows; override only what differs
      • rows: Cordis plugins and their config, the same rows the Loader runs
      • Validated by @webboxes/blends-core; the lock pins every plugin by version and checksum
      # registry/blends/acryl.music/blend.yaml (real)
apiVersion: blends.acryl.dev/v1alpha1
kind: Blueprint
metadata:
  id: acryl.music
  name: Music
  version: 0.1.0
  category: creative
  license: MIT
  visibility: public
spec:
  runtime: cordis
  extends: acryl.blank
  rows:
    - id: brand
      name: acryl-brand
      config:
        name: Music
        tagline: Say the beat, hear the beat.
    - id: acryl-music
      name: acryl-music

      Write a piece once. Everyone can reuse it.

      Compose

      An app is rows of Cordis plugins. Add, override or remove one without forking anything.

      Lock

      blend.lock.json pins every plugin: a local folder by content hash, npm by integrity, a pulled plugin by source and sha512.

      Share

      Push a plugin or a whole app to git or a registry, private or public. Others pull it by name, verified.

      Reuse and grow

      acryl new --from starts from anyone's app; the agent inside adds plugins; a snapshot records it all again.

      The same packages run ACRYL and the open framework: @webboxes/blends-core, @webboxes/plugin-hub, @webboxes/app-persistence on npm, MIT.
